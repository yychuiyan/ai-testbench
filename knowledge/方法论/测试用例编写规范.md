# 测试用例编写规范

## 1. 目的

统一测试用例的设计思路、编写格式与评审标准，使用例具备**可执行、可评审、可追溯、可复用**四项基本属性，降低因个人习惯差异导致的漏测与返工。

## 2. 适用范围

| 项       | 说明                                                           |
| -------- | -------------------------------------------------------------- |
| 适用对象 | 功能测试、接口测试、集成测试、回归测试用例的编写与评审         |
| 适用角色 | 测试工程师（编写）、测试负责人（评审与基线）、开发（需求澄清） |
| 不适用   | 性能脚本、自动化代码本身的实现规范（另见对应专项规范）         |
| 生效方式 | 新编写用例强制遵守；历史用例在回归迭代中逐步整改               |

## 3. 术语与职责

- **用例**：描述一次可独立执行、结果可判定的验证活动。
- **用例集**：按模块 / 版本 / 场景聚合的用例集合，是对外引用（@）的最小单位。
- **基线**：评审通过并冻结的用例集，修改需走变更记录。
- **职责边界**：编写人对内容正确性负责；评审人对覆盖完整性与可执行性负责；测试负责人对基线与覆盖率负责。

## 4. 总体设计原则

1. **单一验证点**：一条用例只验证一个明确的业务规则或结果，便于定位失败原因。
2. **可独立执行**：任何用例都应能在不依赖其它用例执行结果的前提下运行；共享条件通过「前置条件」声明，禁止写成「用例 A 执行成功后再执行本条」。
3. **结果可判定**：预期结果必须是可观测、可量化的（页面提示文案、字段值、状态码、数据库值、日志关键字），禁止出现「正常」「无异常」「符合预期」等无法判定的表述。
4. **数据具体化**：涉及输入的用例必须给出具体测试数据或明确的数据构造规则，禁止出现「输入合法的用户名」。
5. **正反成对**：每个功能点至少覆盖 1 条正常流与 1 条异常流。
6. **可追溯**：用例必须关联需求编号 / 用户故事编号，支持双向追溯。
7. **避免冗余**：同一等价类的重复验证只保留一条代表性用例；通过组合与边界扩展覆盖，而非堆数量。
8. **可维护**：模块调整、界面改版时，用例的修改范围应局部化，避免一改牵动全量。
9. **分层适度**：单元 / 接口层可验的逻辑不重复下沉到 UI 层，UI 用例聚焦端到端业务流程。

## 5. 用例要素与编写要求

每条用例至少包含以下要素，编写要求如下：

| 要素           | 编写要求                                       | 常见问题                           |
| -------------- | ---------------------------------------------- | ---------------------------------- |
| 用例编号       | 全局唯一，见第 7 节命名规则                    | 编号重复、序号跳号                 |
| 用例标题       | 一句话概括「条件 + 动作 + 结果」，长度 ≤ 50 字 | 标题写成功能名，如「登录功能测试」 |
| 所属模块       | 与需求模块 / 用例集目录一致                    | 模块层级随意，无法定位             |
| 用例类型       | 功能 / 接口 / 兼容 / 安全 / 性能 / 异常        | 类型缺失，回归时无法筛选           |
| 优先级         | P0—P3，见第 10 节                              | 全部标 P0                          |
| 前置条件       | 系统状态、账号权限、数据准备、依赖服务         | 把操作步骤写进前置条件             |
| 测试数据       | 具体值或构造规则，注明是否需脱敏               | 引用生产真实用户数据               |
| 操作步骤       | 原子化、可执行，见第 9 节                      | 一步包含多个动作                   |
| 预期结果       | 与步骤一一对应，可观测可量化                   | 步骤 5 条、预期 1 条               |
| 关联需求       | 需求 / 缺陷 / 接口文档编号                     | 留空，无法追溯                     |
| 设计人与评审人 | 姓名与日期                                     | 缺失，责任不清                     |
| 备注           | 环境限制、自动化可行性、已知风险               | 空白                               |

## 6. 设计方法选用指引

| 方法            | 适用场景                                       | 输出要点                                |
| --------------- | ---------------------------------------------- | --------------------------------------- |
| 等价类划分      | 输入域大、取值范围明确的字段                   | 有效类 + 无效类，各取代表值             |
| 边界值分析      | 数值、长度、日期、分页、额度                   | 取 min-1、min、min+1、max-1、max、max+1 |
| 判定表 / 因果图 | 多条件组合决定一个结果（如优惠叠加、审批规则） | 枚举条件组合，标注不可达组合            |
| 场景法          | 端到端业务流程（下单、退款、开户）             | 基本流 1 条 + 备选流 / 异常流若干       |
| 状态迁移        | 有明确状态机的对象（订单、工单、任务）         | 覆盖合法迁移 + 非法迁移拦截             |
| 正交 / 因子组合 | 多参数配置组合（机型 × 系统 × 网络）           | 用正交表压缩组合数                      |
| 错误推测        | 经验性高风险点（并发、幂等、超时、重复提交）   | 结合历史缺陷清单补充                    |

方法选用原则：**同一功能点至少使用两种方法**，优先使用可推导出覆盖完整性的方法（等价类、边界值、判定表），错误推测仅作补充。

## 7. 编号与命名规范

**编号格式**：`TC-<模块编码>-<功能编码>-<三位序号>`

- 示例：`TC-ORD-CREATE-001`
- 模块编码与功能编码取自需求模块字典，全大写、不超过 8 个字符
- 序号在功能编码内连续递增，用例删除后序号不回收、不复用
- 跨版本迭代的新增用例沿用同编号规则，不得重排历史编号

**标题句式**：`[前置场景] 在 <条件> 下，当 <操作> 时，应 <预期结果>`

- 正例：`在库存为 0 时，提交订单应返回「商品已售罄」且订单状态为创建失败`
- 反例：`订单测试`、`测试库存不足的情况`（缺少动作与可判定结果）

## 8. 步骤与预期结果编写要求

1. **一步一动作**：每步只做一件事，禁止「打开页面并输入账号密码后点击登录」。
2. **步骤可执行**：写明操作对象与操作值，不依赖读者猜测（点击哪个按钮、输入什么内容）。
3. **预期对应**：每一步或每一组汇聚步骤都必须有对应预期结果，数量与步骤匹配。
4. **可量化**：涉及金额、数量、时间、状态码、文案时给出精确值或明确范围。
5. **长度控制**：单条用例步骤建议 3—8 步，超过 10 步应拆分为多条用例；单条用例执行时长控制在 5 分钟以内。
6. **不做多断言混装**：一次操作产生的多个校验点若可独立失败，应拆分为多条用例，便于缺陷定位。
7. **含数据校验时**：明确校验位置，如「查询订单表 status 字段值应为 PAID」。

## 9. 覆盖策略

按需求条目建立「需求—用例」追溯矩阵，逐条确认覆盖情况。单功能点建议覆盖以下维度：

| 维度       | 覆盖要求                               |
| ---------- | -------------------------------------- |
| 正常流     | 主流程完整走通，含边界内的典型值       |
| 异常流     | 非法输入、服务异常、超时、失败回滚     |
| 边界       | 上下限、空值、最大长度、特殊字符       |
| 权限       | 无权限、越权、角色差异、未登录         |
| 状态与幂等 | 重复提交、并发操作、状态非法迁移       |
| 数据一致性 | 前端展示与后端存储、缓存与数据库一致   |
| 兼容       | 按项目约定的浏览器 / 机型 / 分辨率矩阵 |
| 安全       | 注入、敏感信息暴露、越权访问、日志脱敏 |
| 易用性     | 提示语、错误引导、必填校验时机         |

覆盖要求：P0 / P1 需求 100% 覆盖；整体需求覆盖率 ≥ 95%；未覆盖项必须在使用例集中登记原因（如低风险、需求变更、暂不支持）。

## 10. 优先级与执行策略

| 优先级 | 定义                              | 执行策略                       |
| ------ | --------------------------------- | ------------------------------ |
| P0     | 阻塞级主流程、核心资损 / 安全相关 | 每次构建必执行（冒烟集）       |
| P1     | 重要功能、关键异常分支            | 提测回归必执行                 |
| P2     | 一般功能、次要异常、常见边界      | 版本回归执行                   |
| P3     | 极端边界、罕见组合、易用性细节    | 按需执行，可放入探索性测试清单 |

优先级判定规则：影响交易、资金、数据正确性的最低为 P1；主流程不可用即为 P0。禁止将未评估的用例默认标为 P0。

## 11. 测试数据设计规范

1. 数据应与用例同源存放，注明构造方式（手工造数 / 脚本 / 接口 / 数据库初始化）。
2. 禁止直接引用生产环境真实用户数据；确需生产数据时须经脱敏并取得授权。
3. 需要账号、权限、额度的用例，须写明账号来源与角色。
4. 可复用的公共数据（如基础商品、标准用户）集中维护，避免每条用例重复描述。
5. 涉及时间敏感逻辑（如优惠有效期、账单周期）时，须写明时钟基准或时间偏移量。

## 12. 编写与评审流程

1. **需求分析**：拆解需求为可验证的验收点，形成检查清单。
2. **用例设计**：按第 6 节方法生成用例，标注优先级与追溯关系。
3. **作者自检**：使用第 13 节检查清单逐项核对。
4. **交叉评审**：由非同作者、熟悉该模块的成员评审；抽样比例不低于 30%，P0 / P1 用例 100% 评审。
5. **评审会**：对分歧条目当场结论；争议项由测试负责人裁定。
6. **修订与基线**：评审意见 1 个工作日内闭环，通过后标记基线版本。
7. **回归补充**：线上 / 测试缺陷修复后，必须补充对应用例，并标明来源缺陷编号。

评审通过标准：P0 / P1 无未决争议、覆盖率达标、无歧义表述、数据与前置条件完整。

## 13. 评审检查清单

- [ ] 标题体现条件、动作、结果，长度合规
- [ ] 编号唯一、符合命名规则、序号连续
- [ ] 每条用例关联需求编号，追溯矩阵无缺口
- [ ] 前置条件、测试数据完整且可复现
- [ ] 步骤原子、可执行，无隐含前置
- [ ] 预期结果可观测、可量化，与步骤一一对应
- [ ] 正常流与异常流成对覆盖
- [ ] 边界值包含上下限及越界值
- [ ] 权限与并发、幂等场景已考虑或有登记
- [ ] 优先级划分符合第 10 节规则
- [ ] 与既有用例无重复或冲突
- [ ] 敏感数据已脱敏

## 14. 常见反模式与整改

| 反模式                 | 问题             | 整改方式                             |
| ---------------------- | ---------------- | ------------------------------------ |
| 「验证功能正常」       | 结果不可判定     | 写明具体字段值、状态码、提示文案     |
| 一步含多动作           | 失败无法定位     | 拆成原子步骤或拆分用例               |
| 一条用例覆盖多规则     | 断言混装         | 按单一验证点拆分                     |
| 依赖其它用例的执行状态 | 无法独立运行     | 状态写入前置条件或数据准备步骤       |
| 全部标记 P0            | 回归成本失控     | 按第 10 节重新分级                   |
| 用例即界面操作流水账   | 业务规则覆盖缺失 | 补充等价类、边界值、判定表推导的用例 |
| 只有正向用例           | 缺陷逃逸率高     | 每功能点补齐异常与边界               |

## 15. 维护与变更

1. 需求变更后 2 个工作日内完成受影响用例的更新，并在备注中记录变更来源。
2. 用例失效（功能下线）时标记为「废弃」并保留编号，禁止直接删除，避免追溯断链。
3. 基线用例的每次修改保留版本记录：修改人、日期、原因。
4. 每季度对高频失败、长期未执行的用例做一次清理复盘。
5. 用例集按模块 + 版本组织，便于通过 @ 引用复用。

## 16. 质量度量指标

| 指标           | 定义                             | 目标值                 |
| -------------- | -------------------------------- | ---------------------- |
| 需求覆盖率     | 已覆盖需求条目 / 需求总条目      | ≥ 95%                  |
| 用例评审通过率 | 一次评审通过条目 / 送审条目      | ≥ 85%                  |
| 用例执行通过率 | 通过条目 / 执行条目              | 用于趋势观察，非考核项 |
| 缺陷发现占比   | 用例执行发现缺陷 / 阶段缺陷总数  | 反映用例有效性         |
| 用例失效率     | 因用例描述错误导致的无效执行次数 | 逐版本下降             |
| 平均执行时长   | 单条用例平均耗时                 | ≤ 5 分钟               |

## 17. 附：提交前自检清单

1. 我能否在不问作者的情况下独立执行这条用例？
2. 失败时，我能否仅凭预期结果判断是产品缺陷还是用例问题？
3. 这条用例是否与已有用例重复验证了同一个等价类？
4. 该功能点的正常、异常、边界、权限是否各有代表用例？
5. 用例是否关联了明确的需求编号与优先级？
