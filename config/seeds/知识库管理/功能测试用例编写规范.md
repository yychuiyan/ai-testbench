# 功能测试用例编写规范

## 1. 目的

统一功能测试用例的编写口径、粒度与质量标准，使用例可以被不同人员独立执行、评审和复用，做到需求覆盖有追溯、执行结果可判定、回归维护成本可控。

## 2. 适用范围

- 适用：Web、App、小程序、服务端 API 等**功能测试**用例的设计与编写，以及用例的评审、维护与归档。
- 不适用：性能、安全、兼容性等专项测试的详细设计文档；自动化脚本的代码实现规范（另行约定）。

## 3. 角色与职责

| 角色                   | 职责                                                   |
| ---------------------- | ------------------------------------------------------ |
| 用例作者（测试工程师） | 按本规范编写用例、提交前自检、按评审意见修订、持续维护 |
| 测试负责人             | 组织评审、判定准出、抽检用例质量、维护基线             |
| 产品经理               | 确认需求口径与验收标准，裁决需求歧义                   |
| 开发负责人             | 澄清实现细节与边界行为，确认异常返回口径               |

## 4. 基本原则

1. **单一意图**：一条用例只验证一个测试点，失败时能直接定位问题范围。
2. **可判定**：预期结果唯一、可观察、可量化，禁止出现「正常」「合理」「基本可用」等模糊描述。
3. **可独立执行**：不依赖其他用例的执行结果与执行顺序；需要依赖时必须写入前置条件。
4. **可复现**：前置条件、测试数据、环境信息完整，任何人按步骤执行都能得到同一结果。
5. **可追溯**：每条用例关联需求编号或验收标准编号。
6. **可维护**：描述与实现解耦（不写死按钮坐标、不依赖 UI 文案以外的临时样式），需求变更时可快速定位受影响用例。

## 5. 编写流程

| 步骤 | 动作                                           | 产出物         |
| ---- | ---------------------------------------------- | -------------- |
| 1    | 需求解读，逐条拆出可验证点                     | 测试点清单     |
| 2    | 场景拆解：主流程、分支、异常、边界、权限、状态 | 场景清单       |
| 3    | 选择设计方法并派生用例                         | 用例草稿       |
| 4    | 按本规范自检并补齐数据                         | 可评审用例集   |
| 5    | 同行评审 + 产品确认                            | 评审记录与意见 |
| 6    | 修订闭环，纳入版本基线                         | 基线用例集     |

进入评审的前提：需求已评审通过、测试点清单已覆盖全部验收标准。

## 6. 设计方法选用

| 方法            | 适用场景                                   |
| --------------- | ------------------------------------------ |
| 等价类划分      | 输入域明确的表单、查询条件、枚举值         |
| 边界值分析      | 数值、长度、时间、分页、金额上下限         |
| 判定表 / 因果图 | 多条件组合的业务规则（优惠叠加、审批策略） |
| 正交试验        | 多参数组合且组合量过大的配置类功能         |
| 场景法          | 端到端业务流程，覆盖基本流与备选流         |
| 状态迁移        | 订单、工单、审批等有状态机流转的功能       |
| 错误推测        | 历史缺陷高发模块、并发操作、重复提交       |

规则：每个功能至少覆盖「主流程 + 分支流程 + 异常流程 + 边界值」四类场景，缺一不可。

## 7. 粒度与拆分规则

- 一个测试点对应一条用例，禁止把多个互不相关的验证点塞进同一条用例。
- 用例长度以「单一意图、失败可精确定位」为第一判据，**步骤条数仅作辅助信号**。
- 建议单条用例的执行步骤控制在 **10 步以内**；UI 类用例的公共步骤（登录、进入菜单、造数）统一提取为前置条件，不计入步骤数。
- **超过 15 步必须按业务阶段拆分**：拆分后的用例需说明编号与依赖关系，依赖一律写入前置条件，禁止写成「承接上一条用例」。
- 步骤数少于 3 步不作为「过短」的判定依据，但需确认已包含必要的输入构造与结果校验。
- 例外：场景法产出的端到端链路用例，经测试负责人确认后可保留长链路，需在用例中标注「E2E，不拆分」及不拆分原因。
- 单条用例执行时长建议不超过 5 分钟；超过则按业务阶段拆分。
- 同类校验可合并为参数化用例（如多个字段的必填校验），但失败时必须能直接定位到具体字段。
- 同一前置条件重复出现 3 次以上时，抽取为公共前置，在文档中统一定义后引用。

## 8. 命名与编号

- 命名格式：`项目_模块_测试对象_场景_序号`
- 示例：`CRM_客户管理_新增客户_手机号格式校验_001`
- 要求：名称可自解释，看到名称即可判断验证内容；禁止使用「用例1」「测试A」「新用例」「xxx」等无意义命名。
- 需求变更导致用例语义变化时，同步更新名称与编号，不保留错误名称。

## 9. 步骤与预期结果描述

步骤以动词开头，写明操作对象、具体输入值与操作方式；预期结果写成「操作 — 可观察结果」一一对应的形式。

| 反例             | 问题               | 正例                                                                           |
| ---------------- | ------------------ | ------------------------------------------------------------------------------ |
| 输入正确的手机号 | 无具体值，不可复现 | 在「手机号」输入框输入 `13800138000`，点击「保存」                             |
| 页面显示正常     | 不可判定           | 页面顶部提示「保存成功」，列表首行出现客户「张三」，客户编号非空               |
| 测试异常情况     | 场景不明确         | 断开网络后点击「提交」，提示「网络异常，请稍后重试」，且不生成工单记录         |
| 验证权限         | 未说明账号与预期   | 用「只读角色」账号访问订单详情页，「编辑」按钮不可见；直接调用编辑接口返回 403 |

附加要求：

- 涉及接口时，写明请求方法、路径与关键入参，预期包含 HTTP 状态码与业务错误码。
- 涉及数据变更时，写明需校验的表/接口与关键字段的变化值。
- 涉及异步流程时，写明等待条件与超时上限，禁止使用固定 sleep 作为判定依据。

## 10. 测试数据规范

- 数据显式化：所有输入数据、初始数据、校验数据均在用例中给出，不依赖执行人的临时记忆。
- 每类数据同时给出**合法值、边界值、非法值**，非法值需说明非法原因。
- 禁止使用真实用户个人信息；必须使用脱敏或专用测试账号。
- 数据准备方式需写明（接口造数、脚本、SQL、环境工具），并注明是否可在同一环境下重复执行。
- 用例执行后需说明数据清理要求，避免污染后续回归。

## 11. 优先级与执行分层

| 优先级 | 定义                                   | 执行时机       | 建议占比 |
| ------ | -------------------------------------- | -------------- | -------- |
| P0     | 核心业务链路、冒烟必过项、阻断性场景   | 每次构建必执行 | ≤10%     |
| P1     | 主流程与关键业务分支、资金/权限相关    | 每轮提测必执行 | 30%~40%  |
| P2     | 边界值、异常处理、权限校验、配置组合   | 版本提测后执行 | 40%~50%  |
| P3     | 低频场景、易用性、提示文案、非关键兼容 | 上线前择优执行 | ≤10%     |

分层维护三个集合：**冒烟集（P0）**、**回归集（P0+P1，含历史缺陷用例）**、**全量集（P0~P3）**。缺陷修复后新增的用例默认进入回归集。

## 12. 需求追溯

- 每条用例必须映射到需求编号或验收标准编号，映射关系在评审前完成。
- 需求覆盖率要求 100%；无法验证的需求项需注明原因与替代验证方式，由测试负责人确认。
- 需求变更时，先更新映射关系，再更新用例内容，避免出现无主用例与无用例需求。

## 13. 评审与准出

评审关注点（逐项确认）：

1. 测试点是否覆盖全部验收标准与隐含分支；
2. 预期结果是否唯一可判定；
3. 前置条件与数据是否完整、可复现；
4. 是否存在重复用例或可合并用例；
5. 优先级划分是否合理，P0 是否覆盖核心链路；
6. 命名与编号是否符合规范。

准出指标（全部满足方可纳入基线）：

- 需求覆盖率 100%，P0/P1 用例评审通过；
- 评审意见全部闭环，无遗留「待确认」项；
- 超长用例（>15 步）已拆分或已标注 E2E 例外，冗余用例比例低于 5%；
- 每条用例可独立执行，无跨用例强依赖。

## 14. 维护与变更

触发更新条件：需求变更、功能下线、生产问题暴露用例缺失、缺陷反馈用例描述歧义、环境或数据规则变化。

变更要求：

- 用例作废不删除，标记状态为「已作废」并注明作废时间、原因与替代用例。
- 每次修改记录变更人、变更时间与变更摘要，保证可回溯。
- 按版本纳入基线；回归集随缺陷修复同步更新。
- 每季度对全量用例做一次抽检，清理失效与长期未执行用例。

## 15. 常见反模式（禁止出现）

- 一条用例验证多个无关功能点；
- 预期结果写「显示正确」「功能正常」等无法判定的表述；
- 用例之间强依赖执行顺序（如「承接上一条用例数据」）；
- 用固定等待时间代替条件判定；
- 只写正向流程，不写异常与边界；
- 直接抄写需求原文作为用例名称，无法体现验证动作；
- 测试数据写「任意手机号」「随机金额」，导致结果不可复现。

## 16. 提交评审前自检清单

- [ ] 已覆盖需求全部验收标准，并建立追溯关系
- [ ] 主流程、分支、异常、边界四类场景齐全
- [ ] 每条用例只验证一个测试点
- [ ] 命名与编号符合 `项目_模块_对象_场景_序号` 格式
- [ ] 前置条件、测试数据完整且可重复执行
- [ ] 步骤为动词开头的可执行操作，含具体输入值
- [ ] 预期结果唯一、可观察、可判定
- [ ] 无跨用例依赖，无固定 sleep 判定
- [ ] 优先级已标注，P0/P1 已归入冒烟集与回归集
- [ ] 无敏感真实数据，数据清理方式已说明
